# admin-web 比赛型项目总结文档

## 1. 项目一句话介绍

`admin-web` 是 3D 头部建模与 3D 打印业务系统的运营中枢，也是多 Agent 协作过程的可视化控制台。  
它不仅承担订单、设备、库存等后台管理能力，还把 AI 决策、任务流转、异常处理和 3D 模型预览整合到同一个管理界面里。

如果用一句更适合比赛答辩的话来描述：

**这不是一个普通后台，而是把“AI 决策能力”真正接入生产流程的智能运营中台。**

---

## 2. 我们解决的核心问题

传统 3D 打印或 3D 建模业务里，常见的问题不是单点能力不足，而是整条链路割裂：

- 用户订单、模型审核、设备调度、库存消耗往往分散在多个系统里
- AI 可以做分析，但很难真正进入业务闭环
- 出现设备故障、库存不足、参数不合理时，人工介入成本高
- 多 Agent 的协作过程通常只能停留在概念层，缺少可观测、可解释的产品形态

`admin-web` 的价值就在于把这些环节串起来：

- 一端连接真实业务流程
- 一端连接多 Agent 协作能力
- 中间通过可视化和实时交互，把“智能决策”变成可被运营、审核、干预和复盘的系统能力

---

## 3. admin-web 的核心定位

从比赛视角看，`admin-web` 同时承担了 3 个角色：

### 3.1 运营后台

它覆盖了一个 3D 打印业务最关键的管理模块：

- 订单管理
- 订单详情与审核
- 设备管理
- 库存管理
- 数据看板

这说明项目不是只做前台演示，而是考虑了实际运营落地。

### 3.2 生产控制台

`admin-web` 不是只看数据，它还能直接支撑生产动作：

- 审核订单并推进状态流转
- 查看设备当前任务和进度
- 根据库存情况做扣减与补货判断
- 查看模型文件并辅助判断是否适合打印

这让系统具备“进入业务流程”的能力，而不是单纯展示。

### 3.3 Agent 可视化中枢

这是最适合比赛答辩的亮点。

系统单独设计了 Agent 协作可视化模块，支持：

- 展示多 Agent 的职责分工
- 展示 Agent 决策时间线
- 展示节点状态变化
- 展示 Agent 之间的数据流动
- 模拟正常流程、库存不足、设备故障等典型场景
- 切换真实后端数据与本地演示模式

也就是说，我们不仅做了 Agent，还做了 **Agent 的“可解释界面”和“演示界面”**。

---

## 4. 核心功能模块总结

## 4.1 Agent 协作可视化

这是 `admin-web` 最有辨识度的页面。

它把系统中的协调 Agent、调度 Agent、库存 Agent 以图形化方式展示出来，并且能表现：

- 谁在处理任务
- 谁向谁发送消息
- 当前在做什么决策
- 决策结果是什么
- 出错时怎么容错和回退

为了适配比赛演示，这一页支持多种场景模拟：

- 正常订单流转
- 库存不足触发采购
- 设备故障自动重试与重新分配

这一点特别加分，因为评委可以非常直观地看到：

**我们的 Agent 不是抽象概念，而是能被观察、被解释、被演示的协作系统。**

## 4.2 Agent 管理

除了看见 Agent 运行过程，系统还支持对 Agent 做配置管理，包括：

- Agent 名称和角色定义
- 能力列表
- 状态管理
- System Prompt 管理

这意味着项目不仅关注“跑起来”，还考虑了未来的可配置、可维护和可扩展。

## 4.3 数据看板

看板并不是简单统计页，而是围绕生产运营关键指标展开：

- 订单总量
- 待处理订单
- 正在打印的订单
- 当日完成量
- 设备时间线
- 设备利用率
- 库存预测分析

这让系统具备了业务运营视角，可以向评委强调：

**我们做的是一套可持续运营的系统，不是只面向单次演示。**

## 4.4 订单管理与订单详情

订单模块体现了业务闭环能力。

它支持：

- 订单筛选与批量处理
- 查看订单详情
- 审核通过或取消
- 查看状态时间线
- 查看 Agent 决策历史
- 打开 AI 审核助手
- 上传和预览 3D 模型文件

其中，订单详情页非常像“人工审核 + AI 辅助”的协同界面。  
这类设计在比赛答辩时很容易讲出“人机协作”的感觉。

## 4.5 设备管理与 AI 诊断

设备管理不是静态表格，而是贴近真实生产现场：

- 查看设备状态
- 查看当前任务和进度
- 更新设备状态
- 添加新设备
- 通过 WebSocket 接收实时打印进度
- 在设备离线或维护时触发 AI 诊断

更关键的是，系统把设备异常处理产品化了：

- 设备离线时给出排查建议
- 维护状态下给出维修判断
- 支持生成后续处理动作

这类能力让项目从“信息化后台”更进一步，变成“智能化运维后台”。

## 4.6 库存管理

库存模块承担的是打印材料侧的业务管理：

- 材料列表查看
- 库存数量变更
- 补货阈值管理
- 缺货与低库存提醒
- 补货建议提示

它和 Agent 协作页的库存不足演示场景形成了很好的呼应，证明系统设计是完整的，而不是孤立页面。

## 4.7 3D 模型预览

系统内置基于 Three.js 的模型预览组件，支持 STL、OBJ 等常见模型格式的加载、旋转、缩放和进度反馈。

这点非常重要，因为它把项目和真实 3D 业务绑定起来了。  
评委会更容易相信这套系统确实服务于 3D 建模/打印流程，而不是普通管理后台套壳。

## 5. 比赛中最值得强调的亮点

我建议答辩时重点突出下面 4 个亮点。

### 亮点一：把多 Agent 协作过程可视化

很多项目会说自己用了 Agent，但难点其实不在“用了”，而在：

- 怎么让人看懂
- 怎么让系统可解释
- 怎么让协作过程可追踪

`admin-web` 给出的答案是：

- 图形化节点
- 时间线
- 决策解释面板
- 边的消息流动动画
- 实时状态变化

这让 Agent 不再是黑盒。

### 亮点二：把 AI 接入了真实业务流程

我们的 AI 不只是回答问题，而是进入了业务环节：

- 审核订单
- 辅助调整打印参数
- 诊断设备异常
- 参与库存判断和调度流程

也就是说，AI 从“工具”变成了“流程中的角色”。

### 亮点三：同时兼顾演示效果和真实对接

系统不是纯模拟，也不是只能连真实接口。

它同时具备：

- 演示模式，用于比赛现场稳定展示
- 真实数据模式，用于接后端 API 和实时事件流

这让产品同时具备“好展示”和“可落地”两种能力。

### 亮点四：不是单点页面，而是完整闭环

`admin-web` 从订单、设备、库存、Agent、数据看板到 3D 模型预览，形成了一条完整链路。

它体现的是：

**我们不是做了一个 AI 页面，而是做了一套围绕 3D 业务运行的智能管理系统。**

## 6. 技术实现层面的加分点

虽然比赛答辩不必讲太深，但以下内容可以在被追问时用来证明工程能力：

- 前端基于 React 19 + Vite，具备现代化构建能力
- 使用 Ant Design 作为后台 UI 基础，保证管理场景效率
- 使用 Zustand 管理 Agent 可视化状态，保证实时交互清晰
- 使用 Socket.IO 接收实时设备进度和 Agent 事件
- 使用 ECharts 构建运营看板
- 使用 Three.js 实现 3D 模型预览
- 服务层统一封装 API，并做了前后端字段映射和状态适配
- 使用 Error Boundary 提升前端健壮性

这些点结合起来说明：  
这个项目不是“比赛临时拼接页面”，而是具备继续扩展为正式系统的工程基础。

## 7. 为什么说 admin-web 是本项目最适合拿来答辩的部分

如果从整个项目里选一个最适合比赛讲述的模块，`admin-web` 很有优势，原因有三点：

### 7.1 它最容易被看懂

评委不一定会花很多时间理解后端调度逻辑，但他们能立刻看懂：

- 页面结构
- 业务流程
- Agent 在做什么
- 系统如何处理异常

### 7.2 它最能体现“AI + 业务”的结合

单纯的大模型调用不够打动人，真正有说服力的是：

- AI 怎么参与业务决策
- 人怎么介入和接管
- 决策怎么被展示和追踪

这些内容在 `admin-web` 中都能直接看到。

### 7.3 它最适合比赛现场演示

现场演示最怕两件事：

- 页面内容单薄，讲不出层次
- 系统链路太深，一旦某个服务异常就难以继续

`admin-web` 通过可视化页面和模拟场景，天然适合比赛环境。  
即使在真实后端波动的情况下，也仍然可以完整展示核心设计思想。
