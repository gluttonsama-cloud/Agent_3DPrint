# 仓库整理与功能盘点

日期：2026-10-01  
状态：结构提案，待确认后迁移。现有文件尚未移动，未修改业务代码。

## 1. 整理目标与范围

把旧的头部建模与打印管理系统整理成一个边界清楚、入口明确、可以逐块优化的产品目录。
`relief-studio/` 保持现有位置、代码、配置及开发方式。本次不合并两个产品的依赖或启动命令。

此次工作分为三个阶段：仓库结构整理、功能盘点、逐模块重构。
目录迁移本身不代表功能改进；已有源码也不代表功能经过真实联调。

## 2. 现状与直接证据

| 现状 | 依据 | 对整理的影响 |

| 后端存在五套入口 | `backend/src/app.js`、`app.fixed.js`、`app.server.js`、`app.real.js`、`app.llm.js` | 先确认各入口用途和调用关系，不能按名称直接删除 |

| 文档存在过期内容与失效引用 | AGENTS.md 同时描述“尚未包含代码”和“已包含完整代码”，引用的 plan_draft 当前不存在 | 根规则应描述当前产品边界，旧计划作为参考 |

| 生成物与源码混放 | dist、coverage、test-results、日志、tar.gz、backups/node_modules 等 | 分清可再生成产物、运行数据和需要留存的历史资料 |

当前工作区另有三份未跟踪的管理端答辩文档，以及 relief-studio 的两个未跟踪组件。
后续迁移必须保留这些文件，不将它们当作临时垃圾处理。

## 3. 三种整理方式

| 方式 | 工作量与风险 | 适用情况 |
| --- | --- | --- |
| **推荐：按产品集中，再分层** | 需修复脚本、Docker、文档引用；两个产品边界清楚 | 当前多个产品共处一个仓库，后续逐块优化 |
| 保持四个源码目录原位，只整理文档和产物 | 迁移成本低，但根目录仍承担旧产品入口 | 短期必须保持所有外部路径不变 |
| 新建一套系统，旧代码全部归档 | 重写成本高，容易遗漏已经实现的能力 | 产品流程已经决定彻底更换时 |

推荐第一种。先保留四个子系统内部的实现和名称，避免一次同时改变外部路径、内部架构、依赖管理和产品行为。

补充规则：

- 子系统自己的 Dockerfile、测试配置、环境变量示例留在子系统内；产品级编排放 deploy。
- 各子系统继续独立安装依赖，第一轮不引入 npm workspace、共享包或微服务拆分。
- 根目录 `.env` 只核查变量用途，不复制到文档；搬迁时明确 dotenv 的加载工作目录。
- 服务运行日志、上传文件、数据库数据不当作历史源码归档；先确认使用者和备份需求。
- Android 原生工程属于用户端源码，不能与 dist 等构建产物一起清理。
- archive 中的内容退出正式启动和部署路径；正在被引用的文件不得提前归档。
- 后端 agents、services、states 等内部结构暂时保留，逐功能优化时再迁入模块。

## 7. 优化顺序与验收

1. **结构迁移**：完成路径对应表、保留工作区修改、修复引用，使入口可查。
2. **运行基线**：确认唯一正式后端入口，补齐实际使用的依赖，区分演示模式与真实模式。
3. **建模主链 F01—F04**：上传 → 预处理 → 生成 → 预览 → 下载。
4. **交易与履约 F05—F06**：报价 → 下单 → 支付状态 → 订单追踪。
5. **生产管理 F07—F08**：设备任务、库存及真实打印链路。
6. **智能辅助与统计 F09—F10**：在可信业务数据基础上完善 Agent 与可视化。

每块开始时记录：保留的能力、用户不满意的问题、输入输出、依赖、模拟行为、验收场景。
完成后在重构进度中登记实际验证结果；不以文件数量或页面截图判定完成。

结构迁移的最低验收：

- relief-studio 的文件内容与项目入口不因迁移变化。
- 四个子系统源码、原生工程、现有环境文件和未跟踪资料均可找到。
- 所有跨目录脚本、Docker 构建上下文、文档链接和测试配置完成核对。
- 用户端、管理端执行构建；后端执行对应测试，并记录已有失败与迁移引入的失败。
- 以无外部付费调用的模式做启动和健康检查；真实生成、设备和支付分别登记验证状态。
- 历史入口退出主链之前有引用检查与替代关系；未确认的资料保留。
